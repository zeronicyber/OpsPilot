# KB-1101 Jupyter Notebook Kernel Startup Failure

## Incident Mapping

- **Incident:** INC008381110
- **Service:** Python Analytics Platform
- **Priority:** P2

## Problem Description

Jupyter notebooks remain in the starting state because the `analytics-prod` environment no longer contains the `ipykernel` dependency required by the registered kernel specification.

## Symptoms

- Notebook remains in Starting while the gateway websocket is connected.
- Kernel launch fails with `No module named ipykernel`.
- Python interpreter version does not match the kernel specification.
- Kernel pods on `jupyter-kernel-02` restart or enter `CrashLoopBackOff`.

## Root Cause

An environment update removed `ipykernel` from the `analytics-prod` image and left a kernel specification pointing to an incompatible interpreter. The pod starts, but Python cannot initialize the kernel process.

## Diagnostic Procedure

1. Capture the user ID, notebook, kernel ID, host, and environment from the gateway log.
2. Inspect the pod and restart count:
   ```bash
   kubectl -n analytics get pod nb-<user>-* -o wide
   kubectl -n analytics describe pod nb-<user>-*
   ```
3. Verify interpreter and package availability:
   ```bash
   python -c 'import sys; print(sys.executable, sys.version)'
   python -c 'import ipykernel; print(ipykernel.__version__)'
   ```
4. Compare the image digest and package lock with the last known-good `analytics-prod` build.
5. Verify the kernelspec executable points to the supported environment, not a retired Python path.

## Resolution Procedure

1. Hold new launches for the affected image if multiple users are impacted.
2. Add the approved `ipykernel` version to the environment definition and rebuild the immutable image.
3. Rebuild or register the kernelspec against the correct Python interpreter.
4. Publish and deploy the corrected image through the approved change process.
5. Restart the Jupyter kernel deployment and reconnect affected notebooks.

## Validation Steps

- [ ] `ipykernel` imports successfully in `analytics-prod`.
- [ ] Kernelspec and Python interpreter versions match the platform baseline.
- [ ] A canary kernel starts on each active kernel host.
- [ ] A notebook websocket returns status `101`.
- [ ] A test cell executes and saves output successfully.
- [ ] No new kernel restart or startup errors occur during monitoring.

## Prevention Recommendations

- Pin `ipykernel` in the environment lock file and image build.
- Run kernel startup probes after every image update.
- Block image promotion when kernelspec validation fails.
- Monitor kernel startup latency and pod restart counts.

## Estimated Recovery Time

30-60 minutes for image rebuild and rollout; 10-15 minutes for a tested rollback.

## Escalation Guidelines

Escalate to Python platform engineering when more than five users are affected, the registry image is inconsistent, or the corrected image still reports interpreter mismatch.
