# KB-0901 SAS Web Application HTTP 503 Error

## Incident Mapping

- **Incident:** INC008380901
- **Service:** SAS Web Applications
- **Priority:** P2

## Problem Description

Users cannot open the SAS login page because the backend web node pool has exhausted servlet threads and connection capacity. `lb-sasweb-01` returns HTTP 503 when no backend can accept a new request.

## Symptoms

- `/SASLogon` returns HTTP 503 or takes 30 seconds to time out.
- Web response times increase before the outage.
- `sas-web-01` and `sas-web-02` thread pools approach their configured limits.
- Load balancer connection pool becomes exhausted and reports no healthy capacity.

## Root Cause

The SAS Web backend node pool is at capacity. Both original nodes exhaust servlet threads and backend connections, leaving `lb-sasweb-01` unable to route login requests.

## Diagnostic Procedure

1. Capture status code and response time from an external and internal probe:
   ```bash
   curl -sk -o /dev/null -w '%{http_code} %{time_total}\n' https://sas.example.com/SASLogon
   ```
2. Check backend health and pool capacity on `lb-sasweb-01`.
3. Review `sas-web-01` and `sas-web-02` active threads, queue depth, connection pool usage, and upstream timeout logs.
4. Compare node health checks to distinguish a full pool from DNS, TLS, or authentication failure.
5. Preserve access logs, HTTP status counts, response-time percentiles, and the first 503 timestamp.

## Resolution Procedure

1. Declare login impact and drain or hold nonessential traffic if required.
2. Provision approved capacity on `sas-web-03` and `sas-web-04`.
3. Complete readiness and application health checks before adding nodes to `lb-sasweb-01`.
4. Rebalance load-balancer traffic across all healthy nodes.
5. Safely drain or restart saturated nodes after traffic is distributed.
6. Confirm login success and monitor pool utilization before closing the incident.

## Validation Steps

- [ ] All expected web nodes report healthy to the load balancer.
- [ ] `/SASLogon` returns HTTP 200 from multiple probes.
- [ ] Login response times return to baseline.
- [ ] HTTP 503 count remains zero during monitoring.
- [ ] Thread and connection pools remain below saturation thresholds.
- [ ] Traffic is balanced across the active node pool.

## Prevention Recommendations

- Autoscale or add capacity before thread utilization reaches 75%.
- Alert on response-time percentiles, pool utilization, and 503 rate.
- Run synthetic login probes from outside and inside the network.
- Review session timeout and connection reuse settings during capacity planning.

## Estimated Recovery Time

20-35 minutes to provision capacity, rebalance traffic, and validate login health.

## Escalation Guidelines

Escalate to web platform engineering for sustained 503s, loss of all healthy nodes, or repeated pool exhaustion. Engage network support if load-balancer health checks and backend connectivity disagree.
